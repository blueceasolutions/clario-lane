# Clariolane — Feature Ideas

A backlog of feature suggestions, grounded in a read-through of the current codebase (2026-08-12). Grouped by theme, not priority — pick what's worth doing, not a proposed roadmap.

---

## Close the loop on what's already collected

These aren't new ideas — they're places the product already asks the user for something and then doesn't act on it.

- [x] **Filter passage selection by preferred content type.** Onboarding collects `content_type` (fiction / non-fiction / mixed via [content-type.tsx](src/components/onboarding/preferences/content-type.tsx)), but `GET /practice/passage` ([supabase/functions/practice/index.ts](supabase/functions/practice/index.ts)) picks a random passage from the whole table regardless of it. Wire the preference into passage selection.
  **Done:** This needed a prerequisite fix to actually mean anything. `content_type` (and `goals`/`challenges`) are typed as arrays on the frontend (`OnboardingSchema`) but the `users` columns were plain `text`, and `userMutation.ts` inserts via a blind `as unknown as UserTable` cast with no runtime conversion — so a selection like `["fiction","technology"]` was landing in the database as the literal string `'["fiction","technology"]'`, confirmed against a real local Supabase instance. Migration [20260811234608_fix_user_preference_array_columns.sql](supabase/migrations/20260811234608_fix_user_preference_array_columns.sql) converts all three columns to `text[]` (with a defensive `USING` clause covering the three shapes existing data could be in: the default, an already-mangled JSON string, or a bare scalar), and fixes a second bug it surfaced: the `content_types` onboarding option was seeded as `'fictions'` while every fiction passage is tagged `'fiction'` — that option could never have matched anything. `GET /practice/passage` now filters by `tags && content_type` (Postgres array overlap) when the user has a preference, falling back to the full random pool when they don't or nothing matches. Verified end to end against a real local Supabase instance (migration + seed + a live edge function call over HTTP, not just the SQL) for all three cases: preference with matches, no preference, and preference with zero matches.
- [x] **Actually send the reminders users opt into.** `users.daily_reminder` / `reminder_time` / `weekly_summary` are collected at onboarding and toggleable in [NotificationsCard](src/components/settings/NotificationsCard.tsx), but there's no scheduled job and no email template for either — `send-email`'s `EmailRequest.type` only covers `WELCOME` / `PASSWORD_CHANGED` / `SUBSCRIPTION_CREATED` / `SUBSCRIPTION_CANCELLED` / `FEEDBACK_SUBMITTED`. A `pg_cron` job (or a scheduled edge function) plus two new templates would close this loop and directly drives retention.
  **Done:** Added `DAILY_REMINDER`/`WEEKLY_SUMMARY` email types + templates ([templates.ts](supabase/functions/send-email/templates.ts)), and two `pg_cron` jobs running hourly ([20260811235626_add_reminder_emails.sql](supabase/migrations/20260811235626_add_reminder_emails.sql), mirrored in [supabase/schemas/zz_email_triggers.sql](supabase/schemas/zz_email_triggers.sql)): daily reminders fire at each user's own `reminder_time` (hour granularity — there's no per-user timezone stored, so `reminder_time` is interpreted as UTC, a known limitation) and skip anyone who's already practiced that day; weekly summaries fire once a week (Monday) with the trailing 7 days of stats. Both read the destination URL and service-role key from Supabase Vault rather than hardcoding them, and no-op safely if those secrets aren't set — **this needs a one-time manual setup step post-deploy** (`select vault.create_secret(...)` twice, documented in the migration) since I can't put real production secrets in a migration file.

  **Also found and fixed, same root cause:** the *existing* `WELCOME`/`PASSWORD_CHANGED` email triggers had never actually worked. Their `net.http_post` calls used literal placeholder strings (`'YOUR_PROJECT_REF'`, `'YOUR_SERVICE_ROLE_KEY'`) that were never replaced — and separately, both triggers had been silently dropped entirely by a later, unrelated auto-generated migration (`20260202155058_alter_passages_table.sql`, a `db diff` output that concluded they were extraneous because they were never captured in `supabase/schemas/`, only ever hand-written into ad-hoc migrations). So welcome emails and password-changed security alerts have not been sent since 2026-02-02, independent of the placeholder bug. Fixed both using the same Vault mechanism, recreated the missing triggers, and this time added them to `supabase/schemas/` so a future `db diff` won't repeat this.

  Verified end to end against a real local Supabase instance: enabled `pg_cron` locally, seeded local Vault secrets, and confirmed via `net._http_response` that the full chain (cron → SQL selection logic → `net.http_post` → Kong → edge function → template rendering → Resend) works — including the daily-reminder SELECT logic against four scenarios (matches, already-active-today, reminders-off, wrong-hour) and the weekly 7-day stats window. Two test emails did go out for real through the project's actual Resend account during this validation (to a `@test.com`/`@example.com` test address) — deliberate, one-time, and I stopped once the mechanism was confirmed rather than repeating it.
- [x] **Finish or retire Peripheral Vision practice.** It's a defined `PRACTICES` enum value with its own icon and color ([exercise.ts](src/lib/constants/exercise.ts)), but its route just points at `/dashboard/practice` (the index) — there's no actual exercise implemented behind it yet.
  **Done: retired, not finished** — and the reasoning is worth recording since it wasn't a coin flip. Two things pushed this toward retiring rather than guessing at an implementation: (1) the corresponding `exercises` seed row was already commented out ([exercises.sql](supabase/seeds/exercises.sql)), meaning it was never actually shown to a real user despite being fully wired into the enum/icon/color/route constants — dead on arrival, not a regression; (2) its seed description, *"Recall key details from previously read passages to boost memory,"* doesn't describe a peripheral-vision drill at all (that's a memory/recall exercise) — a real mismatch between the name and whatever was originally intended, not just missing implementation. Building *something* under the "Peripheral Vision" name without knowing which of those two (or a third thing) it was supposed to be felt like shipping a guess dressed up as a feature. Removed the enum value, its icon/color/route map entries, the dead `additionalControls` mapping in [controlPanel.tsx](src/components/exercises/shared/controlPanel.tsx), and the commented-out seed row — verified via a full `Record<PRACTICES, ...>` exhaustiveness check (TypeScript) that nothing else referenced it, and confirmed via a real local Supabase reset that the practice list now correctly shows exactly the three real modes. If/when there's an actual design for this, it'll be cheap to build: the three existing reader hooks (RSVP/word-chunking/teleprompter) all now share their timing math via `src/lib/practiceTiming.ts`, so a fourth mode is mostly a new display component away.
- [x] **Use the `goals`/`challenges` onboarding answers for something beyond storage.** They're collected during onboarding ([goals.tsx](src/components/onboarding), [challenges.tsx](src/components/onboarding/preferences/challenges.tsx)) but don't appear to be read anywhere afterward — e.g. to weight which quests get assigned, or to personalize dashboard copy/encouragement.
  **Done:** Used `goals` to personalize the dashboard's hero banner ([src/lib/goalCopy.ts](src/lib/goalCopy.ts), wired into [src/routes/dashboard/index.tsx](src/routes/dashboard/index.tsx)) — the generic "Ready to level up?" headline/subtext is now specific to whichever of the four onboarding goals (Increase Speed / Improve Comprehension / Enhance Focus / Boost Retention) the user picked, falling back to the original generic copy for anyone with no goal set. Deliberately didn't attach a live metric to each goal in the same banner: `focus_score` (the obvious metric for "Enhance Focus") is set once at onboarding to a hardcoded `92` and never updated again anywhere in the codebase, and there's no tracked metric for "Boost Retention" at all — showing a number there would mean fabricating progress that isn't real, so the copy stays qualitative for those two. `challenges` remains collected-but-unused for now: it was fixed at the storage level (see the content-type item above, same underlying bug affected all three columns) but I didn't find a second, similarly clean touchpoint for it in the time this session had — a reasonable, explicit stopping point after four features rather than something I'd stretch to justify. Verified end to end: `getGoalBannerCopy` is unit tested (7 tests covering all four goals, multi-select priority, unrecognized entries, and the empty/null fallback), and I confirmed via a real local Supabase insert — the same code path `userMutation.ts` uses — that `goals` now round-trips as a real array rather than the mangled string it was before the Feature 1 fix.

## Practice & content

- [x] **User-supplied content.** Paste a URL or plain text to practice on, instead of only the built-in passage library — this is likely the single most-requested feature for a speed-reading tool (people want to read *their* stuff faster, not just canned passages).
  **Done: plain-text paste, not URL import.** Scoped down from the original idea — URL import needs a server-side fetch + Readability-style HTML extraction pipeline (most sites block client-side CORS fetches, and raw HTML isn't practice-ready text), which is a meaningfully bigger, separate piece of work. Paste-your-own-text covers the actual "practice on *my* stuff" need without it.

  Added a "Practice with your own text" entry point on `/dashboard/practice` ([custom-passage-modal.tsx](src/components/dashboard/practice/custom-passage-modal.tsx)) — paste text (30-word minimum), optional title, pick a mode, and it drops straight into the existing RSVP/Teleprompter/Word Chunking readers unchanged. Getting this to fit cleanly took three real fixes, not just a new modal:
  - `usePracticeStore.passage` is normally populated as a side effect *inside* the `fetchPassage` query function itself ([fetchPassage.ts](src/integration/queries/fetchPassage.ts) calls `usePracticeStore.setState(...)` directly from `queryFn`) — an unusual pattern to design around. Added `setCustomPassage`/`isCustomPassage` to the store, and gated the query in all three reader hooks with `enabled: !isCustomPassage` so a fetched random passage can't clobber the pasted one.
  - Custom text has no comprehension questions, but `ComprehensionQuiz.tsx` assumed `questions` was always non-empty (`passage!.questions!`). It now auto-submits the session (comprehension defaulted to 100 — no assessment happened, so no penalty) as soon as the exercise UUID resolves, instead of rendering an empty quiz.
  - `passage_id` was `z.string()` (required) end to end — frontend type, edge function schema, and the RPC arg type in `supabase_types.ts` — because every session was assumed to reference a real `passages` row. Custom passages are intentionally never persisted there (no RLS path for users to insert into `passages` either), so made it nullable at all three layers; the DB column and `record_practice_session` SQL already accepted NULL without changes.
  - Also fixed a real latent bug found while doing this: session submission read the passage id from `queryClient.getQueryData([fetchPassageKey])` (the React Query cache) rather than the Zustand store, a second, independently-stale source of truth for the same value — switched it to read from the store, which both flows populate correctly.

  Verified against a real local Supabase instance at every layer: called `record_practice_session` directly via RPC with `p_passage_id: null` (session recorded, XP awarded, achievement unlocked), confirmed the `practice_sessions` row actually has `passage_id = NULL`, and repeated the same call through the real `POST /practice/session` edge function endpoint (not just the RPC) to exercise the Zod validation layer too. `pnpm test`/typecheck/build all clean.
- [x] **Passage library / browse mode.** A "choose your passage" screen instead of always getting a random one, filterable by topic, difficulty, and length.
  **Done:** New `/dashboard/practice/browse` route ([browse.tsx](src/routes/dashboard/practice/browse.tsx)), reachable from a "Browse passages" button next to the custom-text one added for the item above. Filters by topic (derived from the actual set of tags in use, not a fixed list), difficulty, and a length bucket (short/medium/long, computed client-side from word count since there's no stored length column) — all pure, unit-tested logic in [passageFilters.ts](src/lib/passageFilters.ts). Filtering happens client-side over the full passage set in one query ([fetchPassagesLibrary.ts](src/integration/queries/fetchPassagesLibrary.ts)), the same pattern already used for the other small reference tables (challenges, goals) — no new backend surface needed since `passages` already has an RLS policy allowing authenticated reads.

  Reused the `setCustomPassage`/`enabled: !passage` mechanism built for the item above, but generalized it: added a sibling `setSelectedPassage` store action for a *real* browsed passage (real id, real questions, normal quiz flow, `isCustomPassage` stays `false`) as opposed to pasted text (no id, no questions, `isCustomPassage: true`). The reader hooks' fetch-gate condition changed from `!isCustomPassage` to `!passage` so both flows skip the random-fetch the same way, for the same reason — one prerequisite fix now serves two features.

  Verified against a real local Supabase instance: the exact query `fetchPassagesLibrary` runs (`select * from passages order by created_at desc`, RLS-permitted for anon/authenticated) returns the real seeded passages with their real tags/difficulty/questions, confirming the filter dropdowns and passage cards will be populated from real data. The actual session-recording path a browsed passage flows into afterward (real `passage_id`, real quiz) is unchanged, already-verified code from earlier in this session, so didn't re-test that specific path again. 44/44 tests pass, clean typecheck, clean build (route correctly code-split into its own chunk).
- [x] **Bionic-reading display mode** (bold the first few letters of each word) as an option alongside the existing font/theme settings — complements RSVP/teleprompter rather than competing with them.
  **Done:** Added a "Bionic Reading" toggle to Settings ([ReadingPreferencesCard.tsx](src/components/settings/ReadingPreferencesCard.tsx)), synced to a new `user_preferences.bionic_reading` column the same way `theme`/`font_face`/`font_size_scale` already are ([20260812004622_add_bionic_reading_preference.sql](supabase/migrations/20260812004622_add_bionic_reading_preference.sql)). The actual bold-prefix splitting is pure, unit-tested logic in [bionicReading.ts](src/lib/bionicReading.ts) (word-boundary tokenizing that preserves original whitespace exactly, plus the bold-length heuristic).

  Applied it in exactly one place — [DisplayText.tsx](src/components/exercises/shared/DisplayText.tsx) — rather than in each reader's display component: all three modes (RSVP, Word Chunking, Teleprompter) already render every word or passage of text through that one shared component, so making it bionic-aware there covers all three for free with zero changes to `RSVPDisplay`/`WordChunkDisplay`/`ScrollingTextDisplay` themselves.

  One pre-existing architecture wrinkle surfaced along the way, noted rather than fixed: font settings actually live in *two* parallel, independently-persisted stores — `useDisplaySettingsStore` (`fontFamily`/`fontSize`, which `DisplayText` already read) and `useSettingsStore` (`fontFace`/`fontSizeScale`/`theme`, which the Settings page and `user_preferences` table use). Added `bionicReading` to the latter, since that's the one with the Settings-page pattern and DB sync this needed — but didn't attempt to unify the two stores, which is a separate, larger, unrelated cleanup.

  Verified: 53/53 tests pass (9 new, including whitespace-preservation round-trip checks), and confirmed the `user_preferences.bionic_reading` upsert against a real local Supabase instance — same call shape `setBionicReading` makes, correct default (`false`), correct persistence.
- [x] **Difficulty-adaptive passage selection beyond WPM.** `calculateNextWpm` already adjusts speed by comprehension ([adaptiveWpm.ts](src/lib/adaptiveWpm.ts)); extend the same signal to passage *difficulty*, not just pace.
  **Done:** Added `calculateNextDifficulty` right alongside `calculateNextWpm` in [adaptiveWpm.ts](src/lib/adaptiveWpm.ts) — identical comprehension thresholds (≥80% up, <60% down), but stepping one level through `Easy → Medium → Hard` instead of scaling a number, clamped at either end.

  Persisted the same way `next_wpm` already is: a new `users.next_difficulty` column, and `record_practice_session` gained a matching (optional, backward-compatible) `p_next_difficulty` parameter written via `coalesce(p_next_difficulty, next_difficulty)` so a session that omits it — there isn't a client code path that does today, but the RPC is directly callable — leaves the stored value alone rather than nulling it out. `ComprehensionQuiz.tsx` computes it from `passage.difficulty` (falling back to `"Medium"` for custom passages, matching `setCustomPassage`'s existing default) and sends it in the session payload next to `next_wpm`.

  `GET /practice/passage` (the random-passage picker) now reads `next_difficulty` back and layers it onto the existing topic-preference logic as a 4-tier cascade: tags+difficulty → tags-only → difficulty-only → full pool. Each tier only kicks in if the narrower one matched zero rows, so a preference augments the existing topic matching instead of replacing it, and gracefully degrades when the passage pool doesn't have enough entries at a given difficulty (a real concern with only 3 seed passages, one of which is the only two difficulties represented at all — verified this exact fallback: requesting `Hard` against seed data with no `Hard` passages correctly falls through to the full pool instead of erroring).

  Surfaced the new signal on the Results screen (next to the existing "Next Session" WPM display) rather than leaving it as invisible backend plumbing — shows the recommended difficulty with an up/down indicator when it changed from the passage just read.

  One process note: the first pass at the migration was generated via `supabase db diff` per the documented workflow ([supabase/README.md](supabase/README.md)), but the diff also proposed dropping the `pg_cron` extension (still relied on by the reminder-email cron jobs from the "close the loop" work — undeclared in any schema file because `cron.schedule` isn't schema-diffable DDL, not because it's actually unused) plus two genuinely-dead functions (`claim_quest`, `upsert_user_stats`). Discarded that generated file and hand-wrote a scoped migration instead, containing only the column/constraint and the `record_practice_session` signature change — same approach as the [supabase/README.md](supabase/README.md) doc's warning that the diff tool "is not foolproof."

  Verified against a real local Supabase instance end-to-end: `GET /practice/passage` deterministically returns the one `Easy` seed passage when `next_difficulty='Easy'`, falls back to the full pool when `next_difficulty='Hard'` matches nothing, and `POST /practice/session` persists `next_difficulty` through the RPC while a payload that omits it leaves the stored value untouched. 5 new unit tests for `calculateNextDifficulty` (58 total passing).
- [x] **Post-session vocabulary review.** Surface words tied to missed comprehension questions for spaced-repetition review later, instead of discarding that signal after the quiz.
  **Done:** This required a genuinely new data model — `Question` had no per-question vocabulary field, and there's no admin UI for creating real (non-custom) passages, only the 3 hand-authored seed passages ([supabase/seeds/passages.sql](supabase/seeds/passages.sql)). Added an optional `vocabWord` to `Question` ([src/types/misc.ts](src/types/misc.ts)) and hand-picked a vocabulary word tied to each of the 15 seed questions (e.g. "bridge" for the question about consistency bridging vision and reality — "endurance," which is also a direct correct-answer option elsewhere, etc.), since there's no zod/DB validation on question shape anywhere to extend and no form to update — it really is just backfilled seed JSON plus the type.

  New `vocabulary_reviews` table ([supabase/schemas/vocabulary-reviews.sql](supabase/schemas/vocabulary-reviews.sql)), one row per `(user, word)` via a unique constraint, storing the question text and correct answer as review context (denormalized, matching how passages/questions are already jsonb blobs with no separate `questions` table to reference). `ComprehensionQuiz.tsx` computes which answered questions were wrong and have a `vocabWord` (matching `answers[i]` to `questions[i]` since they're answered in order), then upserts them via a second mutation fired from the session mutation's `onSuccess` — kept as a separate, non-atomic step from `record_practice_session` rather than folding it into that already-large RPC again, since losing a vocab capture on a rare failure is low-stakes compared to the session/XP data that RPC exists to protect atomically.

  Scheduling is a small pure function, `calculateNextReviewInterval` in [vocabularyReview.ts](src/lib/vocabularyReview.ts) — same "adjust by a signal" shape as `calculateNextWpm`/`calculateNextDifficulty`: remembering a word doubles its interval (capped at 60 days), forgetting resets it to 1 day. A repeat miss on a word already being tracked resets its schedule via the same upsert (not a separate code path) rather than accumulating duplicate rows.

  New `/dashboard/vocabulary` route (a due-words review list with a reveal-then-mark-remembered/forgot flip-card flow) linked from a "Review vocabulary" button next to "Browse passages" on the practice tab — matched that existing precedent (this app has no sidebar; navigation is a 2-tab pill bar in `Navbar.tsx`, and secondary feature pages like `browse.tsx` are linked from within a tab's content rather than added as new top-level tabs, so this follows the established pattern instead of growing the primary nav).

  Verified end-to-end against a real local Supabase instance, matching the exact request shapes the app's mutations send (including the `on_conflict=user_id,word` query param `supabase-js`'s `.upsert(rows, { onConflict })` adds — a raw upsert without it 23505s on the unique constraint, which is worth knowing since it's easy to miss in a quick manual test): insert-on-miss, dedup-and-reschedule on a repeat miss of the same word, both review outcomes (interval doubling / streak increment vs. reset), and that RLS actually blocks a second user from reading the first user's rows. 6 new unit tests for the scheduling function (64 total passing). Did not attempt live browser interaction (no browser automation tool available in this environment) — verification is DB/API-level, consistent with the rest of this session's approach.

## Motivation & social

- [x] **Streak freeze / repair**, Duolingo-style — spend earned XP or a limited monthly token to protect a streak instead of losing it outright. Pairs naturally with the existing `streak_3`/`streak_7`/`streak_30` achievements.
  **Done:** Went with the XP-purchase half of the two options in the brief (not a monthly free token) — it's fully user-driven and needed no cron/monthly-reset bookkeeping, while still being a concrete, testable "spend earned XP to protect a streak" mechanic. New `user_stats.streak_freezes` counter, and a `buy_streak_freeze()` RPC (200 XP each, capped at 2 held) — put on `user_stats` rather than `users` since that's the table `record_practice_session` already locks with `for update` on every session, and the table the prominent streak UI actually reads (the codebase has `users.streak_days` and `user_stats.current_streak` as two independently-written duplicates of the same value — chose to extend the one already in scope rather than add a third divergent copy).

  Consumption is automatic, inside `record_practice_session`'s existing streak-calc block: today's behavior (`diff_days = 0` same day, `= 1` continues, `>= 2` resets to 1) gains one more branch — `diff_days = 2` with a freeze available continues the streak and spends the freeze, instead of resetting. Missing 2+ days still always resets it; a freeze bridges exactly one missed day, not an indefinite absence, and this was deliberately verified, not just asserted (see below). Achievement unlocking (`streak_3`/`streak_7`/`streak_30`) already re-reads `user_stats` fresh within the same transaction, so it automatically sees the post-freeze streak with no changes needed there.

  Surfaced end-to-end rather than left as silent backend plumbing: a "Buy freeze" button + freeze count on the dashboard's `StreakCounter` card (gated on affordability/cap client-side, enforced server-side regardless), and `record_practice_session`'s new `freeze_consumed` flag is threaded through the `/practice/session` edge function response into a toast ("A streak freeze saved your streak!") the next time one actually fires.

  As with the two prior DB migrations this session, discarded the `supabase db diff`-generated migration (same unrelated `pg_cron`/dead-function drops as before) and hand-wrote a scoped one instead.

  Verified against a real local Supabase instance: `buy_streak_freeze` correctly rejects insufficient XP and blocks a 3rd purchase once at the 2-freeze cap (confirmed XP is untouched on a failed purchase — no partial spend); and, directly manipulating `last_active_date`/`streak_days` to simulate time passing, confirmed a freeze saves a streak across exactly one missed day (consuming one freeze), a 2-day gap with zero freezes still resets to 1 as before, and — importantly — a 3-day gap with 2 freezes *available* still resets to 1 and leaves both freezes unspent, proving freezes don't silently cover longer absences.
- [ ] **Friends & leaderboards.** The achievements/quests schema is already built around per-user progress; a weekly leaderboard among friends (or opt-in global) is a natural, mostly-additive extension.
- [ ] **Head-to-head reading race.** Two users read the same passage at the same time, compare speed/comprehension live at the end.
- [ ] **Seasonal / limited-time quests**, distinct from the existing `daily`/`weekly` quest types in the `quests` table — gives recurring users something new to come back for beyond the standing quest rotation.
