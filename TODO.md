# Clariolane — Improvements & Optimizations

Findings from a codebase audit on 2026-08-04. Each item includes the evidence found and a concrete recommendation. Ordered roughly by priority within each section.

---

## 🔴 System Design / Data Integrity (highest priority)

- [x] **`practice/session` edge function is a non-atomic, multi-step saga.** ([supabase/functions/practice/index.ts](supabase/functions/practice/index.ts))
  A single "save session" request does ~10+ sequential network round trips: read `users` → read `user_stats` → insert `practice_sessions` → RPC `calculate_session_xp` → RPC `calculate_level` → update `users` (streak) → RPC `upsert_user_stats` → fetch **all** quests → **loop** (read + upsert per quest, awaited one at a time) → RPC `update_avg_scores` → RPC `check_and_unlock_achievements`.
  **Risk:** if any step fails after an earlier write committed, the user ends up in a partial state (e.g. session recorded but XP/streak never applied, or a retry double-awards XP — there's no idempotency key). Two sessions submitted close together can also race on the read-then-write of `user_stats`/`users` (lost updates).
  **Recommendation:** Collapse this into a single Postgres function (e.g. `record_practice_session(...)`) invoked via one RPC call, executed inside one transaction. This fixes atomicity and cuts ~10-15 round trips down to 1, which will also meaningfully reduce edge-function latency.
  **Done:** Added `record_practice_session()` ([supabase/migrations/20260811213809_record_practice_session.sql](supabase/migrations/20260811213809_record_practice_session.sql), mirrored in [supabase/schemas/zz_record_practice_session.sql](supabase/schemas/zz_record_practice_session.sql)) — one `SECURITY DEFINER` RPC, one transaction, `FOR UPDATE` locks on `users`/`user_stats` to close the lost-update race, and a `(user_id, exercise_id, start_time)` dedup key + new `practice_sessions.xp_earned` column so a retried request returns the original result instead of double-awarding XP. Uses `auth.uid()` internally rather than a client-supplied user id (the old `upsert_user_stats`-style pattern of trusting a passed-in `_user_id` would let any authenticated caller record sessions for another user directly over PostgREST — flagged separately below). The edge function ([supabase/functions/practice/index.ts](supabase/functions/practice/index.ts)) now makes exactly one RPC call. Verified functionally against a scratch local Postgres loaded with the real schema files (atomicity-on-failure, idempotent retry, streak/quest/achievement math all checked) since Docker wasn't available locally to run `supabase start`/`db diff` — please run those before deploying.

- [x] **N+1 query loop over quests.** ([supabase/functions/practice/index.ts](supabase/functions/practice/index.ts) — the `for (const quest of allQuests)` block)
  For every session save, the function does 2 sequential DB calls *per quest* (`select` then `upsert`), awaited one at a time instead of batched. This scales linearly with quest count and adds latency to every single practice session completion — the most frequent write in the app.
  **Recommendation:** Replace with a single bulk upsert (SQL `INSERT ... ON CONFLICT` from a CTE/JOIN across all quests at once), ideally folded into the same transactional RPC from the item above.
  **Done:** Folded into `record_practice_session()` above — a single `INSERT ... SELECT ... ON CONFLICT` over a `quest_progress` CTE joins all quests against `user_quests` in one statement instead of looping.

- [x] **Errors are swallowed into a generic message with no observability.** (all `supabase/functions/*/index.ts` catch blocks, e.g. `{ success: false, message: "Something went wrong" }`)
  Only `console.error` is used — there's no error-tracking/APM integration anywhere in the repo (no Sentry, no structured logging). When something breaks in production (e.g. the saga above fails halfway), there's no way to know which step failed or for which user without manually digging through Supabase function logs.
  **Recommendation:** Add a lightweight error-tracking integration (e.g. Sentry's Deno/edge SDK) and include enough context (user id, step name) in logged errors to debug production incidents.
  **Done:** Added [supabase/functions/_shared/log-error.ts](supabase/functions/_shared/log-error.ts) and wired it into every catch block across all six edge functions. It always emits one structured JSON line (function, step, user id where available, message, stack) to `console.error` — searchable in the Supabase log explorer today, no setup required — and additionally reports to Sentry once a `SENTRY_DSN` secret is set (`supabase secrets set SENTRY_DSN=...`), via a dynamically-imported `npm:@sentry/deno@^8` so nothing changes for any function until that secret exists. While wiring this up and verifying every function still type-checks (`deno check`), also found and fixed: a pre-existing `hono/cors` import-map gap that broke `deno check` for every function (added `"hono/cors": "jsr:@hono/hono/cors"` to each `deno.json`), and two pre-existing type errors in `supabase/functions/subscription/index.ts` unrelated to this change.

## 🟠 Performance

- [x] **Main JS bundle is 1.69 MB (503 KB gzipped) despite route-based code-splitting.** Verified by running `npx vite build`:
  ```
  dist/assets/index-B613SGJu.js   1,690.04 kB │ gzip: 503.15 kB
  (!) Some chunks are larger than 500 kB after minification.
  ```
  `tanstackRouter({ autoCodeSplitting: true })` is already enabled, so per-route chunks exist, but shared/vendor code (likely `recharts`, `framer-motion`/`motion`, the full Radix UI set, `canvas-confetti`, `react-confetti-boom`) is all landing in one giant chunk loaded on every page, including the marketing landing page.
  **Recommendation:** Add `build.rollupOptions.output.manualChunks` to split heavy libs into their own chunks, and `React.lazy()`-load chart/confetti components so they only load on the progress/victory-screen routes that actually use them, not on first paint of the landing page.
  **Done:** Main chunk is now 1.30 MB / 389 KB gzipped, and — more importantly than the raw number — `recharts` and `canvas-confetti`/`react-confetti-boom` are now completely absent from it (confirmed by grepping the built chunk's contents, not just its size) and no longer appear in `index.html`'s `modulepreload` list at all. The actual root cause wasn't route-splitting itself but barrel files: `@/components`'s `export *` chain transitively re-exported chart/confetti components through `./dashboard` and `./gamification`, so importing anything from that barrel anywhere — including in [src/routes/__root.tsx](src/routes/__root.tsx), which wraps every route — pulled ~450 KB of chart/confetti vendor code into the eager bundle regardless of whether those components were ever rendered. Fixed by (1) `React.lazy()`-loading every chart/confetti usage site ([src/routes/dashboard.tsx](src/routes/dashboard.tsx), [src/routes/dashboard/index.tsx](src/routes/dashboard/index.tsx), [src/routes/dashboard/progress.tsx](src/routes/dashboard/progress.tsx), [src/components/onboarding/reading-test/results.tsx](src/components/onboarding/reading-test/results.tsx), [src/components/exercises/shared/result.tsx](src/components/exercises/shared/result.tsx)) and (2) removing those components from every barrel's `export *` (`ui/index.ts`, `gamification/index.ts`, `dashboard/overview/index.ts`, `dashboard/progress/index.ts`) so no future barrel import can silently reintroduce the same leak — they're only reachable via direct file import now. Deliberately did **not** add `build.rollupOptions.output.manualChunks`: tried it first, and it actively made things worse — grouping `recharts`/`canvas-confetti` into named vendor chunks caused Rollup to inject them as side-effect imports into nearly every chunk (confirmed by grepping chunk contents), including unrelated marketing-page sections, because of how it interacts with TanStack Router's many auto-code-split entry points. Default chunking plus explicit lazy-loading measurably outperformed it here.

- [x] **Duplicate animation libraries: both `framer-motion` and `motion` are dependencies.** ([package.json](package.json) lines 44 & 46)
  These are the same underlying engine (published by the same team) — shipping both very likely duplicates runtime code in the bundle for no benefit.
  **Recommendation:** Standardize on one (`motion` is the current canonical package name) and remove the other; grep for imports of the removed package and migrate them.
  **Done:** Only one file used `framer-motion` ([src/components/dashboard/ui/nav/dashboardTabs.tsx](src/components/dashboard/ui/nav/dashboardTabs.tsx)); migrated it to `motion/react` and removed `framer-motion` from `package.json`/`pnpm-lock.yaml`. Note: this alone didn't move the main bundle's size — see the bundle-size item above for what actually did.

- [x] **PWA precache ballooned to 9.2 MB across 50 entries**, and `maximumFileSizeToCacheInBytes` was manually raised to 5 MB in [vite.config.ts](vite.config.ts) with the comment "to handle full-fidelity SVGs" — i.e. the cache limit was raised to work around unoptimized assets rather than optimizing them.
  **Recommendation:** Run SVGs/images through an optimizer (svgo / vite-imagetools) and revert the inflated cache limit. Precaching multiple megabytes on first load hurts install time, especially on mobile connections — exactly the audience a "read faster" app should care about.
  **Done:** The two offenders were [public/dark_preview.svg](public/dark_preview.svg) (3.9 MB) and [public/light_preview.svg](public/light_preview.svg) (3.1 MB), the landing-page hero screenshots — not vector SVGs at all, but Figma "export as SVG" output: a thin vector wrapper around 11 base64-embedded PNG screenshots, several at up to 1170×4096px (way beyond what's ever displayed). svgo/vite-imagetools don't help here since the payload is raster data, not paths, so they wouldn't meaningfully shrink it. Instead: extracted each embedded PNG, downscaled to a 1600px longest-side cap (still generous for their largest on-page display size of 1568px), re-encoded as WebP at q82, and re-embedded in place (same `<image>` id/width/height/position attributes — only the mime type and pixel data changed, so the surrounding vector composition, filters, and layout are untouched). Verified by rendering both full SVGs to PNG and inspecting them: visually indistinguishable from the originals. `dark_preview.svg` 3.9 MB → 203 KB, `light_preview.svg` 3.1 MB → 194 KB. Reverted `maximumFileSizeToCacheInBytes` in vite.config.ts now that nothing exceeds Workbox's 2 MB default. Precache is now 60 entries / 2.67 MB (was 50 entries / 9.2 MB) — the entry count went up slightly from this session's other lazy-loading work adding more, smaller chunks, but total size dropped ~71%.

- [x] **Devtools are rendered unconditionally in the root route.** ([src/routes/__root.tsx:155-156](src/routes/__root.tsx#L155-L156)) `<TanStackRouterDevtools>` and `<ReactQueryDevtools>` aren't gated behind `import.meta.env.DEV`. These libraries no-op most of their cost in production builds, but it's not guaranteed and it's a one-line fix to make the intent explicit and guarantee zero prod cost.
  **Done:** Both are now `React.lazy()`-loaded behind `import.meta.env.PROD ? () => null : lazy(...)`, wrapped in `<Suspense fallback={null}>`, so production builds dead-code-eliminate the `import()` entirely rather than relying on the packages' own `NODE_ENV` no-op behavior. Confirmed via `vite build` that this was in fact already being tree-shaken correctly (bundle size was byte-for-byte identical before/after) — this change makes that guaranteed rather than incidental, per the recommendation.

## 🟡 Database & Migrations Hygiene

- [x] **8 of 37 migrations are "fix" migrations correcting earlier ones**, several touching the *same* bug repeatedly:
  - `achievement_id` ambiguity fixed 3 separate times: `20251203062637_fix_achievement_permissions.sql`, `20251208000000_fix_ambiguous_achievement_id.sql`, `20251212065703_fix_achievement_id_ambiguity_again.sql`, `20260202180000_fix_ambiguous_achievement_id_final.sql`
  - `user_stats` RLS policy added/fixed/restored/re-fixed 4 times across `20251203230000`, `20251208000001`, `20251212065251`, `20260202170000`
  This pattern strongly suggests migrations are being written and pushed directly without a local test pass first.
  **Recommendation:** Adopt the `supabase start` local dev loop + `supabase db diff` before pushing any migration touching RLS or function signatures. The repo already has `supabase/schemas/` as a declarative source of truth — lean into the declarative-schema + diff workflow fully rather than hand-writing incremental patches. Now that the schema has stabilized, consider a one-time squash of the migration history.
  **Done:** Added [supabase/README.md](supabase/README.md) documenting the `schemas/` → `supabase db diff` → local `db reset` loop, and committed the `supabase:start`/`supabase:stop`/`supabase:reset`/`dev:supabase` npm scripts that were already sitting uncommitted in `package.json` (they're exactly this workflow — just wired them up properly). This session's own DB work leaned on exactly this: `supabase/schemas/` had also drifted from the actual migration history independent of this TODO item (`z_gamification_functions.sql` still had the pre-fix ambiguous `achievement_id` signature, silently reintroducing the bug in a fresh `db diff`/rebuild even though every real migration had long since fixed it) — see the `record_practice_session` commit. **Not done:** the one-time migration squash. That's explicitly a "consider," and doing it safely means coordinating against whatever's actually recorded in `supabase_migrations.schema_migrations` on the deployed project, which isn't something I can verify without a live project connection (no Docker/linked project available in this environment) — left as a deliberate follow-up in the README rather than guessed at.

## 🟢 Code Quality & Consistency

- [ ] **Zero automated tests.** No `*.test.*`/`*.spec.*` files exist anywhere in `src`, no test runner is configured, and there's no `test` script in [package.json](package.json). This app computes XP/leveling/streak/comprehension-multiplier logic and handles Paystack subscription webhooks — exactly the kind of logic that regresses silently without tests.
  **Recommendation:** Add Vitest and start with the highest-value, easiest-to-break logic: XP/level calculation, streak calculation (`updateStreak` in [supabase/functions/practice/index.ts](supabase/functions/practice/index.ts)), and the RSVP/word-chunking timing math in `src/store/practice` and `src/components/exercises`.

- [x] **A few call sites bypass the integration/query layer** and call the Supabase client directly instead of going through `src/integration/queries`/`mutations`:
  - [src/components/exercises/shared/useSyncDisplaySettings.ts:17](src/components/exercises/shared/useSyncDisplaySettings.ts#L17)
  - [src/components/exercises/shared/ComprehensionQuiz.tsx:174](src/components/exercises/shared/ComprehensionQuiz.tsx#L174)
  - [src/hooks/use-claim-quest.ts:12](src/hooks/use-claim-quest.ts#L12)
  This is inconsistent with the rest of the app's data-fetching pattern (TanStack Query wrapping a dedicated queries/mutations layer) and makes it harder to apply uniform caching/error handling later.
  **Recommendation:** Route these through the existing `integration/queries`/`mutations` layer for consistency.
  **Done:** Extracted `displaySettingsMutation` and `claimQuestMutation` into `src/integration/mutations/`, matching the existing `mutationOptions({ mutationKey, mutationFn })` pattern used by `sessionMutation`/`userMutation` (side-effect callbacks like the quest's `onSuccess` toast/invalidation stay at the call site, same as the existing convention — only the raw Supabase call moved). `useClaimQuest`'s stale `// @ts-ignore - claim_quest might not be in generated types yet` came out too: `claim_quest` was already in `supabase_types.ts`'s `Functions` map, so the ignore was dead weight. Also found and fixed a same-class violation in `ComprehensionQuiz.tsx` one call away from the cited line 174 (a direct `.from('exercises').select('id').eq('exercise', ...)` query at the old line 95) — routed through the already-existing, already-cached `fetchPractices` query instead of adding a new one.

- [ ] **28 occurrences of `: any` / `as any` in `src/`** despite `strict: true` in [tsconfig.app.json](tsconfig.app.json). Worth an audit pass to see which are load-bearing (e.g. third-party type gaps) vs. avoidable.

- [x] **Loosely-typed Hono handlers in edge functions.** [supabase/functions/practice/index.ts:1](supabase/functions/practice/index.ts#L1) opens with `// deno-lint-ignore-file no-explicit-any` and every route handler is typed `(c: any)`, discarding Hono's built-in request/response type safety.
  **Done:** Gave the `Hono` instance a proper `Env` generic (`Variables: { supabase: SupabaseClient<Database>; user: User }`) matching what the auth middleware actually `c.set()`s, dropped every `(c: any)`/`(c: any, next: any)` annotation in favor of Hono's inference, and removed the now-unneeded `deno-lint-ignore-file no-explicit-any` pragma. `c.get("supabase")`/`c.get("user")` are now properly typed at every call site instead of `any`. Verified with `deno check`/`deno lint` (both clean, 0 errors). Checked the other five edge functions too — only `practice/index.ts` had this pattern; the rest already avoid explicit `any` on their handlers.

- [x] **Remove `build_log.txt` from the repo.** It's a stray `pnpm build` log (62 lines) sitting at the repo root, and it's already stale/misleading — it documents a Rolldown/`react-is` resolution failure that no longer reproduces (confirmed via a fresh `npx vite build`, which now succeeds; `react-is` is already a direct dependency). Delete it and add `build_log.txt` to `.gitignore`.
  **Done:** removed, and `build_log.txt` added to `.gitignore`.
- [x] **Verify `deno.lock` at the repo root is still the file Supabase Edge Runtime actually uses.** The Deno edge functions live under `supabase/functions/`; double-check this root-level lockfile isn't orphaned/stale relative to that directory.
  **Done:** it's orphaned — removed. It's not authoritative for anything: the frontend locks dependencies via `pnpm-lock.yaml`, the only CI workflow ([.github/workflows/build-deploy.yaml](.github/workflows/build-deploy.yaml)) only runs `npm install`/`npm run build` and never touches Supabase functions, and Supabase Edge Functions resolve dependencies per-function from each `supabase/functions/*/deno.json` import map (wired up via `import_map` in [supabase/config.toml](supabase/config.toml)) with no root lockfile involved. The file's own contents confirmed this: it was a stale mix of pure frontend npm packages (`@radix-ui/*`, `@tanstack/react-router`, `vite-plugin-pwa`, etc. — deps `supabase/functions/` never imports) alongside a handful of edge-function deps, which only happens because running a bare `deno` CLI command (`check`/`lint`/`cache`) anywhere under the repo walks up and reuses whatever `deno.lock` it finds first — in this case the root one, left behind by some earlier one-off command. Added `deno.lock` to `.gitignore` so this doesn't silently reappear.
